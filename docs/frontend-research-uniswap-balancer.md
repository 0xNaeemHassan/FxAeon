**Source snapshot date:** 3 October 2026. Repositories were read through GitHub's public repository/tree/raw endpoints at their `main` branch commit shown below; citations pin those commits rather than a moving branch.

- [Uniswap/interface](https://github.com/Uniswap/interface), default branch `main`, commit [`47a07f1932d95565f5445c1e62046df69e7994dc`](https://github.com/Uniswap/interface/commit/47a07f1932d95565f5445c1e62046df69e7994dc).
- [balancer/frontend-monorepo](https://github.com/balancer/frontend-monorepo), default branch `main`, commit [`a984883256b43478ba5e6dac6e704a99c3307ae1`](https://github.com/balancer/frontend-monorepo/commit/a984883256b43478ba5e6dac6e704a99c3307ae1).

This is a bounded review of selected web swap/trade quote, step, gas, and read-query code. It is not a repository-wide audit and does not cover Uniswap's mobile/extension clients or every Balancer app/package.

## What the source does

### Query identity, freshness, and quote reuse

Uniswap's trade-service query key contains a validated trade input and a separate settings object for custom slippage, selected protocols, and V4 hook-pool enablement. The source comments that these settings affect quotes even though the query function reads them indirectly, so they are deliberately part of cache identity. That query sets `enabled`, but does not set `staleTime`, `gcTime`, or a query-level retry policy in this hook; those values come from shared React Query defaults. The query function does not consume React Query's `AbortSignal`, so this wrapper establishes key isolation but does not establish transport cancellation. See [Uniswap trade query options, lines 11–53](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/packages/uniswap/src/features/transactions/swap/hooks/useTrade/useTradeServiceQueryOptions.ts#L11-L53).

For this Uniswap snapshot, route quote construction is delegated to its `TradeService` and `@universe/api` stack. The separate prefetch store only handles chained transaction plans: it clears the previous prefetch, keeps one plan for 15 seconds, checks that trade/earn reuse identity still matches, and discards a plan when trade terms drift. It is a useful short-lived, identity-checked optimization, not the source of swap quote truth. See [Uniswap plan prefetch store, lines 12–72](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/packages/uniswap/src/features/transactions/swap/plan/prefetchedPlanStore.ts#L12-L72).

Balancer's simulation key serializes amount, swap direction, token pair, chain, and pool IDs; its build key adds account, chain, slippage, and simulation response. The simulation hook debounces amount changes by 300 ms, enables only for a nonzero settled amount, sets `gcTime: 0`, and caps retries at two (with no retry for one known too-small-wrap error). The build query is enabled only after connection and a simulation result, also has `gcTime: 0`, and both hooks apply `onlyExplicitRefetch`, which disables refetch on mount, reconnect, and window focus. Neither hook consumes a query `signal`; cancellation of the underlying route request is not established by these wrappers. See [Balancer swap query keys, lines 5–34](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/modules/swap/queries/swapQueryKeys.ts#L5-L34), [simulation query, lines 23–69](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/modules/swap/queries/useSimulateSwapQuery.ts#L23-L69), [build query, lines 25–88](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/modules/swap/queries/useBuildSwapQuery.ts#L25-L88), and [the explicit-refetch helper and 300 ms debounce constant, lines 1–26](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/shared/utils/queries.ts#L1-L26).

### Allowance and execution steps

Uniswap generates an ordered step list and processes it in a sequential saga loop. Token approvals/revocations, Permit2 signatures/transactions, and swap calls are separate step types; each step is awaited before the next is handled. The code explicitly associates supported routing variants with the appropriate step. See [Uniswap swap saga, lines 1324–1447](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/apps/web/src/state/sagas/transactions/swapSaga.ts#L1324-L1447).

Balancer composes relayer approval/signature, ERC-20 approval steps, optional Permit2 signature or approval steps, and the swap step. Its step builder supports nesting approvals into an atomic transaction batch for capable accounts; in that case the standalone approval rows are hidden while gasless signatures remain visible. This is a richer account-abstraction/batching path than a basic wallet flow. See [Balancer step inputs and approval collection, lines 77–142](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/modules/swap/useSwapSteps.tsx#L77-L142) and [ordering and optional nested batching, lines 176–251](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/modules/swap/useSwapSteps.tsx#L176-L251).

Uniswap's wallet send callback switches to the transaction's chain, refreshes its provider reference after that switch, and then merges service-produced gas fee parameters into the send request. Its gas helper estimates approval gas when possible and uses a display fallback when estimateGas cannot succeed, with a separate guard when contract lookup fails. See [Uniswap send callback, lines 65–106](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/apps/web/src/features/Swap/hooks/useSendCallback.ts#L65-L106) and [approval/wrap gas display, lines 14–65](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/apps/web/src/state/routing/gas.ts#L14-L65). This is not a source for FxAeon's transaction bounds; each wallet and route has different execution requirements.

### Reads, batching, RPC, and polling

Balancer's `useMulticall` groups reads by chain, runs one query per chain, and calls viem `multicall` with an optional batch size. This bounds the fan-out and lets results for chains settle independently. Its app also exposes an origin-checked `/api/rpc/[chain]` route; the server-side handler reads `NEXT_PRIVATE_DRPC_KEY` and uses it to build the upstream URL. The credential stays on that proxy boundary rather than in the browser bundle. See [Balancer multicall hook, lines 1–43](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/modules/web3/contracts/useMulticall.ts#L1-L43), [RPC route, lines 1–24](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/apps/frontend-v3/app/api/rpc/%5Bchain%5D/route.ts#L1-L24), [server-only dRPC key use, lines 1–25](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/shared/utils/internal-api/rpc.ts#L1-L25), and [dRPC URL mapping, lines 1–47](https://github.com/balancer/frontend-monorepo/blob/a984883256b43478ba5e6dac6e704a99c3307ae1/packages/lib/shared/utils/rpc.ts#L1-L47).

Uniswap's watched transaction plans poll their API after a 10-second initial delay, then every 10 seconds; the polling guard requires a pending, non-final plan younger than one hour. See [Uniswap plan polling constants, lines 21–26](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/packages/uniswap/src/features/transactions/swap/plan/planPollingUtils.ts#L21-L26) and [poll eligibility, lines 158–160](https://github.com/Uniswap/interface/blob/47a07f1932d95565f5445c1e62046df69e7994dc/packages/uniswap/src/features/transactions/swap/plan/planPollingUtils.ts#L158-L160).

## Comparison with FxAeon

The local FxAeon comparison uses checkout HEAD [`6c7d99c88d36bd3f39655105d8d816cc47b362bc`](https://github.com/0xNaeemHassan/FxAeon/tree/6c7d99c88d36bd3f39655105d8d816cc47b362bc) plus the present working-tree changes; the upstream citations are pinned snapshots, while the local links refer to the inspected checkout. FxAeon already follows several of these principles:

| --- | --- | --- |
| Quote/prefetch identity | Trade prefetch uses a single in-memory entry keyed by session, wallet, chain, market, side, token, exact amount, leverage, slippage, bounds, and block. It expires after 10 seconds and validates the current descriptor again before use. The trade page delays prefetch 220 ms and invalidates it when the form changes or leaves foreground. The repo already implements this for Trade. Apply the same explicit input inventory if other flows add prefetching. |
| Query freshness and resume | Wallet Query defaults use 15 s staleness, 60 s cache retention, one retry, foreground-only interval behavior, and focus/reconnect refetch. fxSAVE claimable data uses 60 s staleness/45 s polling; wallet balances poll every 60 s. Canonical asset polls drop to 30 s per chain only when that chain's websocket is not live. Balancer's no-focus-refetch setting is useful for quote/build state that must not silently change under an open review; it should not replace FxAeon's explicit foreground recovery for ordinary reads. |
| Cancellation and stale responses | Read queries accept TanStack `AbortSignal`; old wallet-session queries are cancelled and removed. A post-receipt read cancels pre-receipt work before re-fetching. Trade-prefetch cancellation is logical invalidation/generation fencing, not transport abort; late plans are rejected by identity/descriptor checks. [Wallet query signals and after-receipt invalidation](../apps/mini-app/src/lib/web3/walletQueries.ts#L55-L125), [session cancellation](../apps/mini-app/src/components/WalletDataProvider.tsx#L55-L71), [prefetch invalidation](../apps/mini-app/src/lib/fx/routePrefetch.ts#L80-L145). | Where a new quote backend supports abort, forward the query signal. For the current SDK-local planner, keep the existing identity and late-result guards; do not mistake cache invalidation for cancellation of an RPC already in flight. |
| Approval sequencing | FxAeon validates exact approval destinations, spender, amount, and ordering. The runner estimates each step, requests a wallet signature, records that step kind, waits for its receipt and confirmation, then moves on. [Route validation](../apps/mini-app/src/lib/fx/validation.ts#L78-L136), [sequential execution](../apps/mini-app/src/lib/fx/runner.ts#L500-L660). | Keep approval and action as separate typed steps, with recovery and receipt copy bound to the step type. Uniswap's awaited step pattern maps well. Balancer's atomic approval batching does not map to FxAeon's current Privy/external-wallet path and should not be copied without a deliberate wallet capability and security redesign. |
| RPC and read batching | FxAeon validates each configured provider's host and chain, probes `eth_chainId`, falls back across reviewed endpoints on transient transport/service errors, and stops on reverts/rejections. Wallet reads use `readContracts`/viem multicall where appropriate. ## Architecture limits

Balancer's swap simulations/builds depend on its frontend-specific handlers and SDK, and its main frontend uses an internal RPC proxy backed by dRPC. Uniswap trade quotes are service-backed. Those sources support the general patterns above, but they are not drop-in implementations for FxAeon: FxAeon uses the pinned f(x) SDK as its only protocol planner, builds its static client with browser-visible, chain/host-validated RPC URLs, and has no app backend beyond its optional read-only gas endpoint. Query keys, debounce, short TTL, explicit review, sequential step handling, and read batching transfer as frontend techniques; their backend routing, relayer, Permit2, and account-abstraction machinery does not transfer directly.
